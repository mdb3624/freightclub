## CHG-870: `@EnableMethodSecurity` Exposed a Latent, Systemic Tenant-Context Loss Bug (RESOLVED)

**Origin:** Discovered running the full `npm run test:e2e` suite as part of REVIEWER verification for the Admin persona sprint (US-874, 750-752, 875-878). First manifested as a single failing test — `us-730h-carrier-profile.spec.ts`'s golden path ("fill all 4 tabs, save, reload, data persists") — in code this sprint never touched.

**Initial read (revised below):** first assumed to be a pre-existing, unrelated flake and filed to track separately. Root-caused instead before closing this ticket, because it reproduced deterministically (3/3 local runs, 3/3 CI runs with retries) rather than flaking, which doesn't fit "pre-existing and irrelevant."

**Actual root cause:** this sprint's own `@EnableMethodSecurity` fix (added because `@PreAuthorize` was silently unenforced everywhere — see the sprint's main commit) was the trigger, not an unrelated bystander. `ProfileController.updateProfile()` is gated `@PreAuthorize("@profileService.isOwner(#userId)")`. Enabling method security meant `isOwner()` now genuinely runs as its own `@Transactional` query *before* the controller method's own transaction — for the first time ever. Under Spring Boot's default Open-Session-In-View, one physical DB connection is held for the whole HTTP request across multiple independent `@Transactional` boundaries. PostgreSQL's `SET LOCAL app.current_tenant` (how `TenantAwareDataSource` binds RLS tenant scoping) resets automatically at every `COMMIT`/`ROLLBACK`. So `isOwner()`'s transaction got tenant context correctly (first transaction on the connection) — but the controller method's *own* subsequent transaction, reusing the same physical connection, silently ran with no tenant bound, and RLS failed closed: `updateProfile()`'s internal `findUser(userId)` returned empty, thrown as `IllegalStateException("User not found: " + userId)`, mapped to HTTP 403. Confirmed live via a real network capture: `PUT /api/v1/profile` → 403 → `"User not found: <the caller's own id>"`.

**Why this was invisible before:** with method security never enforced, `updateProfile()`'s own transaction was always the *first* (and only) transactional DB touch of its request, so it always had tenant context. Every `@PreAuthorize("@xService.isOwner(...))")` call site in the codebase (`ProfileController`, `LoadController`, `CarrierProfileService`'s equipment/lane checks, `DocumentService`) was equally exposed to this the moment method security turned on — this was a systemic infrastructure bug, not a one-page defect.

**Fix:** `TenantAwareDataSource` (`backend/src/main/java/com/freightclub/config/TenantAwareDataSource.java`) now wraps every JDBC connection so `commit()`/`rollback()` immediately reapply `SET LOCAL app.current_tenant` afterward, using the same request thread's still-valid `TenantContextHolder` value — proactively covering whatever transaction runs next on that same physical connection, rather than assuming there won't be one. New unit tests (`TenantAwareDataSourceTest`) lock in the reapply-after-commit/rollback behavior directly against a mocked `Connection`.

**Verification:** full backend suite green (955+ tests), full `npm run test:e2e` green (127 passed, 0 failed, 3 pre-existing unrelated skips) — including the originally-failing `us-730h-carrier-profile.spec.ts`, now passing. GitHub Actions CI re-run confirms the same result outside any local environment.

**Disposition:** RESOLVED within this sprint's PR — not deferred, since it was this sprint's own change that exposed it, and every other `@PreAuthorize`-with-bean-method call site in the app shares the same fix.
